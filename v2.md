# v2

a compiled language for application development - backend services, CLI tools, data pipelines. design priorities in order: correctness, readability, productivity, performance.

## compilation

compiles to C. the compiler emits C code, then invokes the system C compiler (cc/gcc/clang) to produce a native binary.

what you get for free:
- every platform that has a C compiler
- decades of optimizer work from gcc and clang
- debugger support (gdb, lldb see through the generated C)
- C library interop with zero bridging cost (the output is C)
- a compiler that can be written in months, not years

compile times are fast because C compiles fast. for development, the compiler can use tcc (tiny C compiler) which compiles at ~10x the speed of gcc but with no optimization. `v2 run` uses tcc by default. `v2 build` uses the system cc with -O2.

the compiler is written in zig. it's a single binary with no runtime dependencies beyond a C compiler.

### build process

`v2 run file.v2` does:
1. parse and type-check file.v2 and all its imports
2. emit a single .c file containing the entire program plus the runtime
3. compile with tcc, execute the result, delete the temp files

`v2 build file.v2 -o myapp` does:
1. same parse and type-check
2. emit .c file
3. compile with cc -O2 -o myapp, delete the .c file

`v2 build --emit-c file.v2` stops at step 2 and keeps the .c file. useful for debugging, inspection, and embedding in C projects.

cross-compilation works if you have a cross-compiler: `v2 build --cc=aarch64-linux-gnu-gcc file.v2`.

### generated C structure

the emitted C is readable. each v2 function becomes a C function. structs become C structs with a GC header. the runtime (GC, scheduler, channel implementation) is emitted inline as static functions at the top of the file. no separate runtime library to link.

```c
// generated from: fn add(a: int, b: int) = a + b
static int64_t v2_add(int64_t a, int64_t b) {
    return a + b;
}
```

heap-allocated types use tagged pointers. the GC header is 8 bytes prepended to every heap object (mark bit, type tag, size).

## memory

### garbage collector

precise generational semi-space collector. two generations: nursery (small, collected frequently) and tenured (large, collected rarely).

**nursery:** a contiguous region (default 4MB). allocation is a pointer bump - increment the allocation pointer by the object size. when the nursery fills, live objects are copied to the tenured generation. dead objects are not touched. this means nursery collection time is proportional to the amount of live data, not the amount of garbage. short-lived allocations (temporaries, intermediate results) cost nothing to collect.

**tenured:** objects that survive multiple nursery collections are promoted here. tenured space is collected less frequently using mark-and-sweep. tenured collections are triggered when tenured space exceeds a threshold (default 64MB, grows dynamically).

**write barrier:** when a tenured object is modified to point to a nursery object, the runtime records this in a remembered set. this allows nursery collection without scanning the entire tenured space. the write barrier is a single branch instruction on every pointer write to a heap object - the cost is measurable but small.

**root scanning:** the collector scans the C stack and all global variables for roots. because the compiler controls the C output, it emits stack maps - metadata that tells the GC exactly which stack slots contain heap pointers at each potential collection point. this makes the collector precise (no false positives from conservative scanning).

**safe points:** GC can only run at safe points where stack maps are available. the compiler inserts safe points at function calls and loop back-edges. a tight loop with no function calls and no back-edge (unlikely but possible with loop unrolling) will not yield to the GC. this is acceptable - such loops are short-lived.

**pause times:** nursery collections are fast (sub-millisecond for typical programs). tenured collections are slower but infrequent. the GC does not run concurrently - it stops all tasks during collection. for the target use cases (backend services, CLI tools), this is the right tradeoff. concurrent collection adds enormous complexity for marginal latency improvement in applications that aren't latency-critical at the microsecond level. if you need zero-pause guarantees, use arenas.

**interaction with tasks:** all tasks share the heap. GC stops all tasks simultaneously (stop-the-world). each task has its own stack, and the GC scans all task stacks for roots. task creation and destruction do not trigger GC - only allocation does.

### value representation

primitives (int, float, bool, byte) are unboxed. they live on the stack or inline in structs. they are never heap-allocated and the GC does not trace them.

everything else is a heap pointer: structs, arrays, strings, maps, closures, enum variants with payloads. these are 8-byte pointers on 64-bit platforms. the GC traces through them.

enum variants without payloads (like `None`, `Point`) are represented as tagged integers, not heap objects.

### strings

immutable. represented as a pointer to a heap-allocated object containing length + byte data. the bytes are UTF-8 but the runtime does not validate encoding on every operation - indexing and slicing operate on bytes. a `chars()` iterator is available for codepoint-aware iteration.

substrings (`slice(s, 0, 5)`) allocate a new string with copied bytes. they do not share the backing buffer. this is simpler and avoids keeping large parent strings alive because a small substring references them.

multi-line strings use triple quotes. indentation is auto-stripped based on the closing `"""` position:

```
query = """
  SELECT *
  FROM users
  WHERE active = true
  """
```

the common leading whitespace (determined by the indentation of the closing `"""`) is removed from each line.

string interning: the compiler interns all string literals. at runtime, strings created by the program are not interned. string equality is byte comparison, not pointer comparison.

`str.builder()` returns a mutable buffer for efficient construction. the builder is GC-managed. calling `builder.build()` produces an immutable `str` and invalidates the builder.

### arenas

arena blocks opt out of the GC for a lexical scope:

```
arena {
  parsed = parse(request.body)
  escape result = transform(parsed)
  temp = scratch()
}
// parsed and temp are freed. result lives on the GC heap.
```

`escape` is a binding modifier. `escape x = expr` deep-copies the value to the GC heap. not just the top-level value - every heap object reachable from it (struct fields, array elements, nested structs) is recursively copied to GC memory. the expression itself runs on the arena like everything else. only the final assignment triggers the copy.

```
arena {
  escape result = transform(parsed)
}
```

`transform` runs entirely on the arena. every allocation it makes internally (local variables, temporaries, intermediate data structures) is arena memory. when it returns, the return value is deep-copied to the GC heap and assigned to `result`. when the arena exits, all arena memory - including everything `transform` allocated - is freed. `result` survives because it's on the GC heap, and every pointer it holds also points to GC memory (from the deep copy).

bindings without `escape` are arena-allocated. if they are referenced after the arena exits - stored in a collection declared outside, assigned to an outer variable, returned from a function - the reference is dangling. this is undefined behavior. the language does not prevent this. the programmer is responsible.

**how arenas work internally:** entering an arena block pushes a new allocator onto a thread-local allocator stack. all heap allocations (struct creation, array growth, string building) check the allocator stack and use the top arena if one is active. when the block exits, the arena's memory is freed in one operation (typically a single `free` call on the backing buffer) and popped from the stack. the GC does not scan arena memory - arena objects are invisible to the collector.

**GC-to-arena references:** a GC-managed object can hold a pointer to an arena-allocated value. when the arena exits, that pointer dangles. this is the programmer's fault. the GC will not crash (it doesn't trace into arena memory) but the program will read garbage if it follows the pointer.

**arena-to-GC references:** an arena-allocated object can hold a pointer to a GC-managed value. this is safe. the GC doesn't know about the arena pointer, but that's fine - as long as the GC value is also reachable from a root (or the arena is still alive), nothing goes wrong. if the only reference to a GC value is from an arena object and the arena exits, the GC value becomes unreachable and will be collected next cycle. this is correct behavior.

**`escape` always targets the GC heap.** regardless of nesting depth, `escape` copies to the GC heap - never to a parent arena. this matters when calling library code from inside an arena. if a library function uses `escape` internally (to keep a cache alive, hold a connection, etc.), that value goes to the GC heap even though the function is running inside your arena. this means an arena block is not a hard guarantee of zero GC allocations - library code can still touch the GC heap via `escape`. but the bulk of work (parsing, transforming, building results) stays on the arena. in practice, libraries use `escape` for long-lived state, not for request-scoped data.

**arena nesting:** arenas nest. inner arenas are freed before outer arenas. allocations go to the innermost active arena.

**the server runtime** wraps each request handler in an implicit arena. all allocations during request processing go to the arena. when the response is sent, one bulk free. the GC is not involved in request processing unless the handler explicitly uses `escape`.

## types

every expression has a known type at compile time. inference handles most cases. if you annotate a type, the compiler checks it. if you don't annotate, the compiler infers it. there is no mode where a type annotation is present but not enforced.

```
x = 5                    // int
name = "alice"           // str
items = [1, 2, 3]        // [int]
scores = {"math": 95}    // {str: int}
active = true            // bool
```

all function signatures are fully explicit. parameter types and return types are required. no return type means void.

```
fn add(a: int, b: int) -> int = a + b
fn greet(name: str) -> str = "hi {name}"
fn log(msg: str) { eprintln(msg) }         // no return type = void
fn load(path: str) -> Config! { ... }      // returns Config or error
```

expression-bodied functions (with `=`) do not need a `return` keyword - the expression is the return value. block-bodied functions (with `{ }`) require explicit `return` for any non-void return. forgetting `return` in a function declared to return a value is a compile error.

closures infer their parameter and return types from context:

```
items.filter(fn(x) x > 0)                 // types inferred from items
items.map(fn(x) -> str { return "{x}" })   // explicit when needed
```

### primitives

| type | meaning | size | heap-allocated |
|------|---------|------|----------------|
| `int` | signed integer | 64-bit | no |
| `float` | IEEE 754 double | 64-bit | no |
| `bool` | true or false | 8-bit | no |
| `byte` | unsigned integer | 8-bit | no |
| `str` | immutable UTF-8 | ptr+len | yes |

explicit-width variants for interop: `i8`, `i16`, `i32`, `i64`, `u8`, `u16`, `u32`, `u64`, `f32`, `f64`. `int` and `float` are always 64-bit regardless of platform.

### structs

plain data. fields are typed. no methods, no constructors, no inheritance.

```
struct User {
  name: str
  age: int
  active: bool
}

user = User { name: "alice", age: 30, active: true }
user.name    // "alice"
```

structs are heap-allocated and GC-managed. field access is a constant offset from the struct pointer (the compiler knows the layout at compile time).

### enums

algebraic sum types. variants can carry typed payloads.

```
enum Shape {
  Circle(float)
  Rect(float, float)
  Point
}
```

variants with payloads are heap-allocated (the payload is stored alongside the tag). variants without payloads are unboxed integers.

generic enums:

```
enum Option(T) {
  Some(T)
  None
}

enum Result(T, E) {
  Ok(T)
  Err(E)
}
```

`Option` and `Result` are defined in the standard prelude. `T?` is sugar for `Option(T)`. `T!` is sugar for `Result(T, str)`. `T!E` is sugar for `Result(T, E)`.

### arrays

growable, GC-managed. element type is homogeneous and inferred.

```
items = [1, 2, 3]           // [int]
push(items, 4)               // requires mut
names = ["alice", "bob"]     // [str]
```

represented as a heap object containing pointer, length, and capacity. elements are stored contiguously. growing beyond capacity allocates a new backing buffer (doubling strategy).

### maps

hash maps. key type must support equality and hashing (all primitive types and strings do). value type is homogeneous.

```
scores = {"alice": 95, "bob": 87}    // {str: int}
scores["alice"]                       // 95
scores["carol"] = 91                  // requires mut
```

represented as a heap-allocated hash table using open addressing with robin hood hashing.

### generics

functions and types can be generic. type parameters are inferred at call sites. the compiler monomorphizes - emitting a separate concrete version for each instantiation. no runtime overhead.

```
fn first(items: [T]) -> T? {
  if len(items) > 0 { return items[0] }
  return nil
}

fn filter(items: [T], pred: fn(T) -> bool) -> [T] {
  mut result: [T] = []
  for item in items {
    if pred(item) { push(result, item) }
  }
  return result
}
```

generic structs and enums:

```
struct Pair(A, B) {
  first: A
  second: B
}

pair = Pair { first: "hello", second: 42 }  // Pair(str, int)
```

monomorphization means generic code is as fast as hand-written concrete code. the tradeoff is binary size - each instantiation produces separate machine code. for the target use cases this is acceptable.

### traits

structural interfaces. a type satisfies a trait if functions with matching signatures exist for it. no `impl` blocks, no `implements` declaration. the compiler checks trait satisfaction at each call site where a trait bound appears.

```
trait Display {
  fn display(self) -> str
}

fn display(u: User) -> str = "{u.name} ({u.age})"
fn display(s: Shape) -> str = match s {
  Circle(r) -> "circle({r})"
  Rect(w, h) -> "rect({w}, {h})"
  Point -> "point"
}

fn print_all(items: [T]) where T: Display {
  for item in items {
    println(item.display())
  }
}
```

**static dispatch (default):** when a function has a trait bound (`where T: Display`), the compiler generates a separate version for each concrete type. inside each version, trait function calls are resolved to direct calls. no indirection, no lookup tables. the compiler knows the exact type.

```
fn print_all(items: [T]) where T: Display {
  for item in items {
    println(item.display())
  }
}

print_all(users)    // compiler generates print_all_User, calls display(User) directly
print_all(shapes)   // compiler generates print_all_Shape, calls display(Shape) directly
```

**dynamic dispatch (opt-in):** sometimes you don't know the concrete type at compile time. you have a list of mixed types, or a function that should accept any type matching a trait. `dyn Trait` handles this.

```
fn log(item: dyn Display) {
  println(item.display())
}
```

`log` accepts any type that satisfies `Display`. it doesn't know which type it got. here's what happens under the hood:

at the call site, the compiler knows the concrete type:

```
log(user)
```

the compiler checks: does `User` satisfy `Display`? it looks for `fn display(u: User) -> str` in scope. found. it builds a vtable - a small table of function pointers - containing the address of `display(User)`. it passes `log` two things: a pointer to the user data, and a pointer to the vtable.

inside `log`, `item.display()` doesn't call a known function. it looks up the `display` entry in the vtable and calls whatever function pointer is there. this is one pointer dereference plus an indirect call - the cost of dynamic dispatch.

`dyn Display` is 16 bytes: 8 for the data pointer, 8 for the vtable pointer. this is sometimes called a "fat pointer."

```
log(user)     // vtable points to display(User)
log(circle)   // vtable points to display(Shape)
```

**when to use which:** use static dispatch (the default) when performance matters and the types are known. use `dyn` when you need type erasure - mixed collections, plugin systems, callback registries where the concrete type varies.

**vtable ambiguity:** if two modules both define `fn display(u: User) -> str`, which one goes in the vtable? the one in scope at the call site where the `dyn` conversion happens. if both are in scope, it's a compile error. resolve it with selective imports.

**trait composition:** a function can require multiple traits:

```
fn serialize_and_log(item: T) where T: Display + Serialize {
  log(item.display())
  write(item.serialize())
}
```

traits cannot have associated types or default implementations. they are purely function signature requirements. this keeps trait resolution simple and error messages readable.

**downcasting from `dyn`:** the concrete type behind a `dyn` pointer is not permanently erased. the vtable stores a type tag. you can recover the concrete type with `as`:

```
fn handle(item: dyn Display) {
  if user = item as User {
    println("found user: {user.name}")
  } else if shape = item as Shape {
    println("found shape")
  }
}
```

`item as Type` returns `Type?` - the concrete value if the type matches, nil if it doesn't. this is a runtime check (one integer comparison on the type tag). the returned value is a regular typed value, not `dyn`.

### function overloading

functions can share a name if their first parameter type differs. the compiler resolves based on the concrete type of the first argument at the call site.

```
fn area(c: Circle) -> float = 3.14159 * c.r * c.r
fn area(r: Rect) -> float = r.w * r.h
```

rules:
- only the first parameter's type participates in overload resolution
- the first parameter's type must be a concrete type (not a generic, not `dyn`)
- if the type is ambiguous at the call site, it's a compile error
- overloaded functions can be `pub` and exported from modules
- importing two modules that both define `fn area(c: Circle)` is a compile error unless one is aliased or the other is not imported

overloading is how traits work in practice. `fn display(u: User)` and `fn display(s: Shape)` are overloads that happen to satisfy the `Display` trait. UFCS makes them feel like methods: `user.display()` resolves to `display(user)` which resolves to the `User` overload.

## immutability

everything is immutable by default.

```
x = 5
x = 6              // compile error

mut y = 5
y = 6              // ok
```

struct fields require `mut` on the binding:

```
user = User { name: "alice", age: 30 }
user.age = 31      // compile error

mut user = User { name: "alice", age: 30 }
user.age = 31      // ok
```

array and map mutation requires `mut`:

```
items = [1, 2, 3]
push(items, 4)     // compile error

mut items = [1, 2, 3]
push(items, 4)     // ok
```

function parameters are immutable. to mutate through a parameter, use `&mut`:

```
fn birthday(u: &mut User) {
  u.age += 1
}

mut user = User { name: "alice", age: 30 }
birthday(&mut user)
```

`&mut` at the call site is required so mutation intent is visible to the reader.

**what `&mut` does not do:** it does not prevent data races. two tasks can hold `&mut` references to the same value simultaneously. the GC prevents memory corruption (the object stays alive), but concurrent mutation without synchronization produces undefined field values. use channels or mutexes for safe concurrent mutation. `&mut` is a readability tag, not a safety guarantee.

## error handling

no null. no exceptions. errors are values. two mechanisms: options for absence, results for failure.

### options

`T?` is sugar for `Option(T)` - either `Some(value)` or `None`. `nil` is sugar for `None`.

```
fn find(users: [User], id: int) -> User? {
  for u in users {
    if u.id == id { return u }
  }
  return nil
}
```

### results

`T!` is sugar for `Result(T, str)`. `T!E` is sugar for `Result(T, E)`. `!` alone is sugar for `void!` (can fail, returns nothing on success).

```
fn parse(raw: str) -> Config! {
  if raw.len == 0 { fail "empty input" }
  return do_parse(raw)
}
```

`fail expr` returns an error from the enclosing function. the expression must match the function's error type (`str` for `T!`, `E` for `T!E`). `fail` is not an exception - it doesn't unwind the stack or search for a handler. it's a return with an error value.

### handling errors and nil

four ways to deal with a `T?` or `T!`:

**`try` - propagate to caller.** if the expression is nil or an error, the enclosing function returns it immediately.

```
fn load(path: str) -> Settings! {
  raw = try fs.read(path)
  config = try parse(raw)
  try validate(config)
  return config
}
```

`try` requires the enclosing function to have a compatible return type. if your function returns `Settings!` you can `try` any expression that returns `T!`. if your function returns `User?` you can `try` any `T?`. if your function returns `void` (no error type), using `try` is a compile error - the error has nowhere to go.

```
fn main() -> ! {
  config = try load("config.json")   // ok: main returns !
  try serve(config)
}

fn main() {
  config = try load("config.json")   // compile error: main doesn't return !
}
```

**`or` - handle locally.** provide a fallback value, or handle the error with access to the error value.

```
config = parse(data) or default_config()
config = parse(data) or |err| {
  log("parse failed: {err}")
  return default_config()
}
user = find(users, 42) or guest_user()
```

**`!` - crash.** unwrap or panic. for cases where failure is a bug, not an expected condition.

```
config = parse(data)!
user = find(users, 42)!
```

**`match` - exhaustive handling.** for typed errors where you want to handle each case.

```
user = find(42) or |err| match err {
  NotFound -> return guest_user()
  ConnectionLost -> fail err
  Timeout -> return try retry(42)
}
```

### try and or are mutually exclusive

`try expr or fallback` is a compile error. they express opposite intent: `try` means "i can't handle this, pass it up." `or` means "i'll handle this right here." pick one. the compiler enforces this.

### optional chaining

`?.` accesses a field or calls a method on a value that might be nil. if the value is nil, the entire chain evaluates to nil.

```
name = find(42)?.name                    // str? - nil if user not found
upper = find(42)?.name.to_upper()        // str? - nil if user not found, otherwise uppercase
city = find(42)?.address?.city           // str? - nil if user or address is nil
```

one `?.` makes the rest of the chain nil-safe. you don't need `?.` on every step - only where a value might actually be nil. `find(42)?.name` uses `?.` because `find` returns `User?`. `.name` is a normal field access because if we got past the `?.`, we have a real User, and User always has a name.

`?.` produces a `T?`. you can then use `try`, `or`, or `!` on the result:

```
name = try find(42)?.name                // propagate if nil
name = find(42)?.name or "anonymous"     // fallback if nil
name = find(42)?.name!                   // crash if nil
```

### typed errors

`T!` uses `str` as the error type by default. for richer error handling, define an error enum:

```
enum DbError {
  NotFound
  ConnectionLost
  Timeout
}

fn find(id: int) -> User!DbError {
  conn = get_conn() or fail ConnectionLost
  row = try query(conn, id)
  return parse_user(row)
}
```

**error type compatibility:** `T!` (string errors) propagate freely between functions returning `U!`. typed errors `T!E` propagate to functions with the same error type. propagating `T!E` to a function returning `U!` (string error) auto-converts via the `Display` trait on `E`. if `E` doesn't implement `Display`, it's a compile error.

### panic vs fail

`panic` and `fail` are different things.

`fail` returns an error value. the caller can handle it with `or`, propagate it with `try`, or crash with `!`. `fail` is for expected failures - file not found, parse error, network timeout. the function's return type must include `!`.

`panic` terminates the task immediately. no recovery, no handling. panics are for bugs - array out of bounds, integer overflow, violated invariants. the task dies, the error is logged. other tasks keep running. you don't catch panics. you fix the code.

```
fail "config not found"       // error: caller decides what to do
panic("unreachable")          // bug: something is fundamentally wrong
```

### truthiness

`nil` and `false` are falsy. everything else (including `0`, empty strings, empty arrays) is truthy. this prevents the class of bugs where `0` or `""` accidentally evaluates as false.

## UFCS

any function can be called with dot syntax on its first argument:

```
fn full_name(u: User) -> str = "{u.first} {u.last}"

user.full_name()    // calls full_name(user)
full_name(user)     // identical

[1, 2, 3]
  .filter(fn(x) x > 1)
  .map(fn(x) x * 2)
  .sort()
```

UFCS resolution order: the compiler first checks for a field with the given name. if no field exists, it looks for a function whose first parameter type matches the value's type. if multiple functions match (overloads), it's resolved by the first parameter type. if still ambiguous, it's a compile error.

## pattern matching

exhaustive. the compiler errors if cases are missing. wildcard `_` catches remaining cases.

```
fn describe(s: Shape) -> str = match s {
  Circle(r) -> "circle r={r}"
  Rect(w, h) -> "rect {w}x{h}"
  Point -> "point"
}
```

pattern matching on values:

```
match status_code {
  200 -> "ok"
  404 -> "not found"
  n if n >= 500 -> "server error: {n}"
  _ -> "other"
}
```

nested patterns:

```
match result {
  Ok(Some(value)) -> use(value)
  Ok(None) -> default()
  Err(msg) -> fail msg
}
```

match is an expression:

```
label = match status {
  Active -> "active"
  Inactive -> "inactive"
}
```

## concurrency

### task model

green threads (tasks) on a work-stealing thread pool. the pool has one OS thread per CPU core by default.

tasks are preemptible. the compiler inserts yield points at function calls and loop back-edges. at a yield point, if the scheduler decides to preempt the task (because it's run too long or another task is ready), the task's stack is saved and another task is resumed. this means a CPU-bound loop does not block other tasks. the yield check is a single load + branch - the cost is negligible.

```
a, b = await_all(
  spawn { fetch_profile(id) },
  spawn { fetch_orders(id) },
)
```

`spawn { expr }` creates a task and returns a `Task(T)` where T is the return type of the block. `Task(T)` is a GC-managed value. you can pass it to functions, store it in arrays, return it.

### awaiting tasks

`await task` blocks the current task until the target task completes. it returns `T!` - the result on success, or a string error if the task panicked.

```
task = spawn { fetch_profile(id) }
// ... do other work ...
profile = try await task
```

handle task errors the same as any result:

```
result = try await task            // propagate error
result = await task or default()   // fallback on failure
result = (await task)!             // crash if task failed
```

`await_all` waits for multiple tasks and returns their results as a tuple:

```
a, b = await_all(
  spawn { fetch_profile(id) },
  spawn { fetch_orders(id) },
)
```

if any task in `await_all` panics, the panic is returned as an error for that position.

### cancellation

`task.cancel()` requests cancellation. it does not kill the task immediately. cancellation is cooperative - the task stops at the next yield point (function call or loop back-edge). a cancelled task's `await` returns `Err("cancelled")`.

```
task = spawn { long_computation() }
task.cancel()
result = await task    // Err("cancelled")
```

if the task has already finished, `cancel()` does nothing. a task in a tight loop with no function calls cannot be cancelled until the loop ends.

### task inspection

`task.done() -> bool` returns true if the task has completed (successfully, with a panic, or cancelled). non-blocking.

```
task = spawn { work() }
while !task.done() {
  println("still working...")
  time.sleep(100)
}
result = try await task
```

### timeouts

`timeout(ms, task)` awaits a task with a deadline. returns `T!` - the task's result if it finishes in time, or `Err("timeout")` if the deadline passes. on timeout, the task is cancelled.

```
result = timeout(5000, spawn { http.get(url) })

match result {
  Ok(response) -> handle(response)
  Err(msg) -> println("request failed: {msg}")
}
```

or with `try`:

```
fn fetch_with_timeout(url: str) -> Response! {
  return try timeout(5000, spawn { http.get(url) })
}
```

`timeout` does not wait the full duration if the task finishes early. it returns the result immediately.

### unwaited tasks

a task that is never awaited runs to completion. if it panics, the error is logged to stderr. if it succeeds, the result is discarded. the GC collects the task when no references remain.

### channels

`Channel(T)` is a typed, bounded, multi-producer multi-consumer queue. it's a GC-managed value that can be passed to functions, stored in structs, and shared across tasks.

```
ch = channel(str, 100)

spawn {
  ch.send("hello")
}

msg = ch.recv()
```

`channel(T, capacity)` creates a channel. T can be any type - primitives, strings, structs, enums, arrays, maps. the channel passes references, not copies. sender and receiver share the same heap object. the capacity is the buffer size - how many values can be sent before `send` blocks.

`ch.send(val)` sends a value. blocks if the buffer is full. panics if the channel is closed.

`ch.recv() -> T?` receives a value. blocks if the buffer is empty. returns nil when the channel is closed and all buffered values have been drained.

`ch.close()` signals no more values will be sent. receivers drain remaining values, then get nil.

channels are iterable. `for msg in ch` receives until the channel is closed:

```
fn producer(ch: Channel(str), items: [str]) {
  for item in items {
    ch.send(item)
  }
  ch.close()
}

fn consumer(ch: Channel(str)) {
  for msg in ch {
    println(msg)
  }
}

fn main() {
  ch = channel(str, 100)
  spawn { producer(ch, ["a", "b", "c"]) }
  consumer(ch)
}
```

multiple tasks can send to and receive from the same channel. the runtime handles synchronization internally.

### match on channels

`match` can wait on multiple channels simultaneously. it blocks until one of the channels has a value ready. the first channel with a ready value wins. if multiple are ready, one is chosen at random.

a channel match is one-shot - it handles one value and exits. wrap in a loop for continuous processing:

```
while true {
  match {
    msg = requests.recv() -> handle_request(msg)
    sig = signals.recv() -> {
      println("shutting down")
      break
    }
    tick = heartbeat.recv() -> send_heartbeat()
  }
}
```

each iteration, the match blocks until one channel is ready, executes that arm, and loops.

`timeout` arm fires if no channel is ready within the given duration:

```
while true {
  match {
    msg = ch.recv() -> process(msg)
    timeout(5000) -> {
      println("idle for 5 seconds")
      break
    }
  }
}
```

the timeout resets every iteration. if messages arrive continuously, the timeout never fires. it only triggers after the full duration of silence. if messages are buffered in the channel, `recv()` wins immediately - timeout only applies when all channels are empty and waiting.

`default` arm for non-blocking checks. executes immediately if no channel is ready:

```
match {
  msg = ch.recv() -> process(msg)
  default -> println("nothing ready right now")
}
```

### mutexes

`Mutex(T)` wraps a value with a lock:

```
counter = Mutex(0)

spawn {
  guard = counter.lock()
  guard.val += 1
  // guard auto-unlocks when it goes out of scope (defer-based)
}
```

`lock()` returns a `Guard(T)` that provides access to the inner value via `guard.val`. the guard unlocks when it goes out of scope. this prevents forgetting to unlock.

### task-GC interaction

the GC stops all tasks during collection (stop-the-world). each task has its own stack. the GC scans all task stacks for roots. task stacks grow dynamically (segmented stacks or stack copying, details are an implementation choice).

## closures

closures capture variables from their enclosing scope by reference. the captured variables are moved to a heap-allocated environment when the closure is created. subsequent reads and writes to those variables (from both the closure and the enclosing scope) go through the environment.

```
fn make_counter() -> fn() -> int {
  mut count = 0
  return fn() -> int {
    count += 1
    return count
  }
}

counter = make_counter()
counter()    // 1
counter()    // 2
```

closure environments are GC-managed.

closures used as arguments to higher-order functions (map, filter, etc.) that don't escape the call are stack-allocated when the compiler can prove it. this is an optimization, not a language guarantee.

## iteration

`for x in thing` works on three types:

**arrays** - iterates over elements by index. the compiler lowers this to a counter-based loop with no heap allocation.

```
for item in items {
  println(item)
}

for i, item in items {
  println("{i}: {item}")
}
```

**channels** - receives values until the channel is closed. see the channels section.

```
for msg in ch {
  process(msg)
}
```

**iterators** - any `fn() -> T?` is an iterator. the for loop calls it repeatedly until it returns nil.

```
fn range(start: int, end: int) -> fn() -> int? {
  mut i = start
  return fn() -> int? {
    if i >= end { return nil }
    val = i
    i += 1
    return val
  }
}

for x in range(0, 10) {
  println(x)
}
```

this is the only iterator protocol. no traits, no special types. a closure that returns `T?` is an iterator. to make a custom type iterable, write a function that returns such a closure:

```
struct FileReader {
  path: str
}

fn lines(f: FileReader) -> fn() -> str? {
  content = fs.read(f.path) or return fn() -> str? { return nil }
  parts = content.split("\n")
  mut i = 0
  return fn() -> str? {
    if i >= len(parts) { return nil }
    line = parts[i]
    i += 1
    return line
  }
}

reader = FileReader { path: "data.txt" }
for line in reader.lines() {
  println(line)
}
```

### break and continue

`break` exits the innermost loop. `continue` skips to the next iteration. neither carries a value. if you need a result from a loop, assign to a variable declared before it:

```
mut found: User? = nil
for user in users {
  if user.name == target {
    found = user
    break
  }
}
```

## equality and comparison

### equality

`==` and `!=` work on all types. the behavior depends on the type:

**primitives** - value equality. `5 == 5` is true. `3.14 == 3.14` is true.

**strings** - byte-by-byte comparison. `"abc" == "abc"` is true.

**structs** - structural equality by default. every field is compared with `==` recursively. if any field's type doesn't support `==`, using `==` on the struct is a compile error.

```
a = User { name: "alice", age: 30 }
b = User { name: "alice", age: 30 }
a == b    // true - same field values
```

**arrays** - element-by-element comparison. same length and all elements equal.

**maps** - same keys and all values equal.

**enums** - same variant and equal payloads.

to override the default equality for a struct, define an `eq` function:

```
fn eq(a: User, b: User) -> bool = a.id == b.id
```

when `eq` is defined, `==` calls it instead of structural comparison.

### comparison and ordering

`<`, `>`, `<=`, `>=` work on primitives and strings (lexicographic). they do not have default behavior for structs.

to make a type orderable, define a `compare` function that returns -1, 0, or 1:

```
fn compare(a: User, b: User) -> int {
  return compare(a.name, b.name)
}
```

once `compare` is defined, the comparison operators work on that type, and the type can be used with `sort()`. trying to use `<` on a type without `compare` is a compile error.

## tuples

tuples are anonymous fixed-size ordered collections. they have typed positions, not named fields.

```
pair = (1, "hello")          // (int, str)
triple = (true, 42, "ok")   // (bool, int, str)
```

access by position:

```
pair.0    // 1
pair.1    // "hello"
```

tuples are the natural return type for functions that return multiple values:

```
fn divmod(a: int, b: int) -> (int, int) {
  return (a / b, a % b)
}

(quot, rem) = divmod(10, 3)
```

tuples support equality if all element types support equality. they do not support ordering.

## destructuring

### tuple destructuring

```
(a, b) = get_pair()
(_, second) = get_pair()    // discard first
```

### struct destructuring

```
user = User { name: "alice", age: 30, active: true }
{name, age} = user          // binds name and age from matching fields
{name, ...} = user          // bind name, ignore the rest
```

struct destructuring matches by field name, not position. the variable names must match field names.

### destructuring in for loops

```
pairs = [(1, "a"), (2, "b"), (3, "c")]
for (num, letter) in pairs {
  println("{num}: {letter}")
}
```

### destructuring in function parameters

```
fn greet({name, age}: User) -> str {
  return "hi {name}, age {age}"
}
```

## numeric conversions

`int` auto-promotes to `float` in mixed arithmetic expressions and when passed to a function expecting `float`. this is safe - no precision loss for integers that fit in a float.

```
x = 5 + 2.0        // float (int promoted)
y = 10 / 3.0       // float

fn distance(x: float, y: float) -> float = sqrt(x * x + y * y)
distance(3, 4)      // ok: 3 and 4 promoted to float
```

`float` to `int` requires explicit conversion. this truncates toward zero:

```
n = int(3.7)        // 3
n = int(-2.9)       // -2
```

narrowing conversions between sized types require explicit conversion:

```
big: int = 1000
small: i8 = i8(big)    // programmer's responsibility if it overflows
wide: int = int(small)  // always safe, widening
```

integer overflow on `int` (64-bit) is a panic in debug builds and wrapping in release builds.

## type aliases

`type` creates an alias for an existing type:

```
type ID = int
type Handler = fn(Request) -> Response
type Headers = {str: str}
type Callback = fn(str) -> !
```

aliases are transparent - `ID` and `int` are the same type. you can use them interchangeably. aliases exist for readability, not for creating distinct types.

## module-level bindings

modules can declare bindings at the top level. they are initialized once at program startup, in source order. cross-module initialization follows import order.

```
imp std/os { env }

db_url = env("DATABASE_URL") or "postgres://localhost/mydb"
max_retries = 3
mut request_count = Mutex(0)
```

module-level bindings are immutable by default. `mut` is allowed but the programmer is responsible for thread safety - use `Mutex` if the value is accessed from multiple tasks.

`pub` module-level bindings are accessible to importers:

```
pub version = "1.2.0"
pub default_port = 8080
```

## default parameters and named arguments

functions can have default parameter values. parameters with defaults must come after parameters without:

```
fn serve(addr: str, port: int = 8080, workers: int = 4) {
  // ...
}

serve("localhost")
serve("localhost", 3000)
serve("localhost", 3000, 8)
```

named arguments allow specifying parameters by name. they must come after positional arguments:

```
serve("localhost", workers: 8)
serve("localhost", port: 3000, workers: 8)
serve("localhost", workers: 8, port: 3000)    // order doesn't matter for named args
```

named arguments are especially useful for functions with multiple optional parameters where you want to skip some:

```
fn request(url: str, method: str = "GET", headers: {str: str} = {}, body: str = "", timeout: int = 5000) -> Response! {
  // ...
}

res = try request("https://api.example.com/users", method: "POST", body: payload)
```

## string operations

string functions are builtins (see prelude) and are used via UFCS:

```
name = "  Hello, World  "
name.trim()                     // "Hello, World"
name.trim().to_lower()          // "hello, world"
name.contains("World")          // true
name.starts_with("  H")        // true

"a,b,c".split(",")             // ["a", "b", "c"]
"hello".replace("l", "r")      // "herro"
"-".repeat(20)                  // "--------------------"
```

## slicing

arrays and strings support slice syntax with `[start..end]`:

```
arr = [10, 20, 30, 40, 50]
arr[1..3]       // [20, 30]
arr[..3]        // [10, 20, 30]
arr[2..]        // [30, 40, 50]

s = "hello"
s[1..4]         // "ell"
s[..3]          // "hel"
```

slicing creates a new array or string with copied data. `start` is inclusive, `end` is exclusive. both are optional - omitting start defaults to 0, omitting end defaults to length.

out-of-bounds slice indices are a panic. negative indices are not supported.

## indexing

```
arr = [10, 20, 30]
arr[0]          // 10
arr[2]          // 30
arr[5]          // panic: index out of bounds

s = "hello"
s[0]            // "h" (single-character string)
s[4]            // "o"

scores = {"alice": 95}
scores["alice"]    // 95 (returns T?)
scores["bob"]      // nil
```

array and string indexing panics on out of bounds. map indexing returns `T?` - nil for missing keys. negative indices are not supported.

## compound assignment

`+=`, `-=`, `*=`, `/=`, `%=` are supported:

```
mut x = 10
x += 5     // 15
x -= 3     // 12
x *= 2     // 24
x /= 4     // 6
x %= 4     // 2
```

compound assignment works on struct fields and array elements when the binding is `mut`.

## bitwise operations

`&` (and), `|` (or), `^` (xor), `<<` (shift left), `>>` (shift right), `~` (not):

```
flags = 0b1010
flags & 0b1100      // 0b1000
flags | 0b0001      // 0b1011
flags ^ 0b1111      // 0b0101
flags << 2          // 0b101000
flags >> 1          // 0b0101
~flags              // bitwise complement
```

bitwise compound assignment: `&=`, `|=`, `^=`, `<<=`, `>>=`.

## containment

the `in` keyword works in `for` loops and as a containment check:

```
if "alice" in names { ... }
if key in scores { ... }
if 42 in numbers { ... }
```

`in` works on arrays (linear search), maps (key lookup), and strings (substring search):

```
if "world" in "hello world" { ... }    // true
```

`not in` is the negation:

```
if key not in scores { ... }
```

## struct update syntax

create a new struct from an existing one with some fields changed:

```
user = User { name: "alice", age: 30, active: true }
updated = User { ...user, age: 31 }
```

this allocates a new struct. all fields are copied from `user` except `age` which is set to 31. the original is unchanged.

## recursive types

structs can reference themselves through optional fields:

```
struct Node {
  value: int
  next: Node?
}

head = Node { value: 1, next: Node { value: 2, next: Node { value: 3, next: nil } } }
```

this works because structs are heap-allocated pointers. `Node?` is an 8-byte pointer (either a pointer to a Node on the heap, or nil). the compiler has no size problem - the struct itself is a fixed size regardless of how deep the chain goes.

## printing and display

### println

`println` is a keyword that prints a readable representation of any value followed by a newline. it has built-in formatting for all types:

```
println(42)                        // 42
println(3.14)                      // 3.14
println("hello")                   // hello
println(true)                      // true
println([1, 2, 3])                 // [1, 2, 3]
println({"a": 1, "b": 2})         // {"a": 1, "b": 2}
println(User { name: "alice", age: 30 })  // User { name: "alice", age: 30 }
println(Circle(5.0))               // Circle(5.0)
println(nil)                       // nil
```

`println` does not require Display. it works on every type, always. this is for debugging and quick output.

### string interpolation and Display

string interpolation uses the `Display` trait:

```
"hello {name}"          // ok: str has built-in Display
"count: {n}"            // ok: int has built-in Display
"user: {user}"          // compile error unless User has Display
```

to make a type work in string interpolation, define `display`:

```
fn display(u: User) -> str = "{u.name} ({u.age})"
"user: {user}"          // "user: alice (30)"
```

all primitive types, strings, arrays, and maps have built-in Display. structs and enums require a user-defined `display` function for interpolation.

the distinction: `println` always works (debug representation). string interpolation requires Display (controlled representation).

## reader and writer traits

`Reader` and `Writer` are traits defined in the prelude for composable I/O. any type that can produce bytes is a Reader. any type that can consume bytes is a Writer.

```
trait Reader {
  fn read(self) -> str!
}

trait Writer {
  fn write(self, data: str) -> !
}
```

files, network connections, TLS connections, string buffers, and HTTP response bodies all satisfy these traits. this means you can write functions that work with any I/O source:

```
fn copy(src: dyn Reader, dst: dyn Writer) -> ! {
  while true {
    chunk = try src.read()
    if len(chunk) == 0 { break }
    try dst.write(chunk)
  }
}

fn read_all(src: dyn Reader) -> str! {
  mut b = str.builder()
  while true {
    chunk = try src.read()
    if len(chunk) == 0 { break }
    b.append(chunk)
  }
  return b.build()
}
```

`str.builder()` satisfies `Writer`. this means you can pipe anything readable into a string buffer, or pipe a string buffer into anything writable.

## error wrapping

errors can be wrapped with context as they propagate. the `wrap` keyword adds a message prefix to an error:

```
fn load_config(path: str) -> Config! {
  raw = try wrap "read config" fs.read(path)
  config = try wrap "parse config" parse(raw)
  return config
}
```

if `fs.read` fails with "file not found", the propagated error becomes "read config: file not found". if `parse` fails with "unexpected token at line 3", it becomes "parse config: unexpected token at line 3".

`wrap` works with `try`. it's not a separate mechanism - it attaches context at the propagation point. the original error is preserved as a suffix after the colon.

for typed errors (`T!E`), `wrap` converts to a string error (`T!`). if you need to preserve the typed error, don't use `wrap` - handle it with `or |err|` and construct a new typed error.

```
fn connect(addr: str) -> Conn!DbError {
  return try net.connect(addr, 5432)  // no wrap: preserves DbError
}

fn connect_logged(addr: str) -> Conn! {
  return try wrap "db connect" net.connect(addr, 5432)  // wrap: converts to string error
}
```

## json field mapping

by default, `json.encode` and `json.decode` use struct field names as JSON keys. for custom key mapping, use `@json` tags on struct fields:

```
struct User {
  @json("first_name")
  first: str

  @json("last_name")
  last: str

  @json("email_address")
  email: str

  age: int  // no tag: uses "age" as the key
}
```

`json.encode(user)` produces `{"first_name": "alice", "last_name": "smith", "email_address": "alice@example.com", "age": 30}`.

`json.decode(data, User)` maps JSON keys to fields using the same tags.

optional fields use `T?`:

```
struct User {
  name: str
  @json("middle_name")
  middle: str?   // omitted from JSON output if nil, allowed to be missing on decode
  age: int
}
```

### all tags

tags are a closed set defined by the language. you cannot create custom tags.

**`@json("key")`** - maps a struct field to a JSON key for `json.encode` and `json.decode`. applied to struct fields.

**`@sql("column")`** - maps a struct field to a database column name for row decoding. applied to struct fields.

```
struct User {
  @json("first_name") @sql("first_name")
  first: str

  @json("email_address") @sql("email")
  email: str

  age: int
}

// JSON: uses @json tags
user = try json.decode(data, User)

// SQL: uses @sql tags
rows = try sql.query(conn, "SELECT first_name, email, age FROM users")
for row in rows {
  user = try sql.decode(row, User)
}
```

**`@deprecated("message")`** - marks a pub function, struct, or enum as deprecated. the compiler warns when it's used. the LSP shows the message in hover. applied to declarations.

```
@deprecated("use find_by_id instead")
pub fn lookup(id: int) -> User? {
  return find_by_id(id)
}
```

**`@packed`** - structs with explicit memory layout. fields are laid out in declaration order with no padding. useful for FFI interop and binary protocols. applied to struct declarations.

```
@packed
struct PacketHeader {
  version: u8
  flags: u8
  length: u16
  seq: u32
}
```

that's it. four tags. the language does not have a general-purpose tag or annotation system.

## integer division

`/` on two integers performs integer division (truncates toward zero):

```
10 / 3       // 3
-7 / 2       // -3
```

`%` is the remainder operator:

```
10 % 3       // 1
-7 % 2       // -1
```

if either operand is a float, the result is a float:

```
10 / 3.0     // 3.333...
10.0 / 3     // 3.333...
```

division by zero is a panic for integers. division by zero for floats produces infinity or NaN per IEEE 754.

## string-number conversion

`int(s)` and `float(s)` parse strings into numbers. they return `T!` since parsing can fail:

```
n = try int("42")         // 42
f = try float("3.14")     // 3.14
n = int("abc")            // Err("invalid integer: abc")
```

number-to-string conversion happens via string interpolation or the `str()` builtin:

```
s = "{n}"          // string interpolation
s = str(42)        // "42"
s = str(3.14)      // "3.14"
```

## map iteration

maps are iterable with `for key, value in`:

```
scores = {"alice": 95, "bob": 87, "carol": 91}

for key, value in scores {
  println("{key}: {value}")
}

for key in scores {
  println(key)       // iterates over keys only
}
```

iteration order is insertion order. maps preserve the order in which keys were first added.

## discarding values

`_` discards a value. multiple uses of `_` in the same scope don't conflict:

```
_ = some_function()
_ = another_function()

(_, second) = get_pair()
(_, _, third) = get_triple()

for _, value in scores {
  println(value)
}
```

if a function returns a non-void value and you don't assign it, the compiler warns. `_ =` explicitly silences the warning. this prevents accidentally ignoring errors:

```
fs.write("out.txt", data)     // compiler warning: unhandled result
_ = fs.write("out.txt", data) // ok: explicitly discarded
```

## doc comments

lines starting with `//` directly above a `pub` declaration are doc comments. `v2 doc` extracts them to generate documentation.

```
// Parse a configuration file from the given path.
// Returns an error if the file doesn't exist or contains invalid syntax.
pub fn parse(path: str) -> Config! {
  ...
}
```

doc comments are plain text. no special syntax, no markdown, no tags. the first sentence is used as the summary in listings. the full text appears on the detail page.

doc comments on non-pub declarations are ignored by `v2 doc` but still visible in LSP hover.

## syntax

no semicolons. newline-terminated. continuation on operators and after opening delimiters (`(`, `[`, `{`, `.`).

```
fn double(x: int) -> int = x * 2

fn process(items: [str]) -> [str] {
  return items
    .filter(fn(s) s.len > 0)
    .map(fn(s) s.trim())
}
```

### for loops

```
for item in items { ... }
for i in 0..10 { ... }
for i in 0..n step 2 { ... }
for i, item in items { ... }    // index + value
```

`0..10` is a range (0 inclusive, 10 exclusive). ranges are not heap-allocated - the compiler lowers them to counter-based while loops.

### while loops

```
while condition { ... }
```

`while` with assignment binds a value and loops until it's nil:

```
while line = readln() {
  process(line)
}
```

this calls `readln()` each iteration. if the result is nil, the loop exits. otherwise `line` is bound to the unwrapped value and the body runs. works with any expression that returns `T?`.

no `do-while`. no `loop`. `while true { ... }` with `break` covers those cases.

### if expressions

`if` is an expression. it returns the value of the taken branch.

```
label = if active { "on" } else { "off" }
```

when used as a statement, the else branch is optional:

```
if err { log(err) }
```

### maps

```
scores = {"alice": 95, "bob": 87}
scores["alice"]          // 95
scores["carol"]          // nil (returns T? for missing keys)

mut scores = {"alice": 95}
scores["bob"] = 87       // insert
delete(scores, "alice")  // remove
```

map key lookup returns `T?`. missing keys return nil, not a panic.

### defer

scoped cleanup. runs when the enclosing scope exits (end of block, return, fail, ? propagation). multiple defers run in reverse order.

```
conn = db.connect()
defer conn.close()

f = fs.open(path)
defer fs.close(f)
// f closed first, then conn
```

defer in a loop runs at each iteration end:

```
for path in paths {
  f = fs.open(path)
  defer fs.close(f)
  process(f)
  // f closed here, each iteration
}
```

### string interpolation

```
"hello {name}"
"result: {compute(x + 1)}"
"{a} + {b} = {a + b}"
```

expressions inside `{}` are converted to strings via the `Display` trait. types without a `display` function cause a compile error inside interpolation.

### comments

```
// line comment
```

no block comments. line comments only.

## modules and visibility

a file is a module. `pub` makes a declaration visible to importers. everything else is module-private.

```
// user.v2
pub struct User {
  name: str
  age: int
}

pub fn validate(u: User) -> bool = u.age > 0

fn helper() { ... }  // not visible outside this file
```

imports:

```
imp std/http                  // namespace: http.get, http.serve
imp std/fs { read, write }    // selective: read, write
imp user { User, validate }   // selective from local file
imp utils/helpers as h        // aliased namespace: h.do_thing
```

`pub struct` makes the struct and all its fields visible. there is no field-level visibility. encapsulation is at the module level - if you need to hide a field, don't make the struct pub and expose accessor functions instead.

### module resolution

1. `imp std/X` - standard library module (compiled into the binary)
2. `imp X` - local file `X.v2` relative to the importing file
3. `imp X/Y` - local file `X/Y.v2` relative to the importing file
4. `imp X` where X matches a package name - external dependency (see packages)

no circular imports. if module A imports module B and module B imports module A, it's a compile error.

### prelude

the following are available in every file without imports:

**keywords:**
- `println`, `print` - write to stdout
- `eprintln`, `eprint` - write to stderr
- `panic` - terminate the task with an error message
- `assert` - panic if condition is false
- `assert_eq` - panic if two values are not equal
- `in` / `not in` - containment checks and for loops

**builtins (collection and string operations):**
- `len(x)` - length of array, map, or string
- `push(arr, val)`, `pop(arr)` - array mutation
- `sort(arr)`, `sort_by(arr, fn)`, `reverse(arr)` - array ordering
- `map(arr, fn)`, `filter(arr, fn)`, `reduce(arr, init, fn)` - array transforms
- `keys(m)`, `delete(m, key)` - map operations
- `split(s, sep)`, `trim(s)`, `contains(s, sub)`, `replace(s, old, new)` - string operations
- `starts_with(s, prefix)`, `ends_with(s, suffix)` - string checks
- `to_upper(s)`, `to_lower(s)` - string case
- `clone(val)` - deep copy
- `type_of(val)` - type name as string

these are all usable with UFCS: `items.len()`, `name.trim()`, `scores.keys()`.

everything else requires an import:

```
imp std/io { readln }
imp std/fs { read, write }
imp std/json { encode, decode }
```

## packages

git-based dependency management. no hosted registry.

### manifest: `v2.pkg`

```
name myapp
version 1.0.0

require (
  github.com/user/router v0.3.1
  github.com/user/json v1.0.0
)
```

versions are git tags. commit hashes work for pinning:

```
require (
  github.com/user/router abc1234
)
```

### lockfile: `v2.lock`

auto-generated. records resolved commit hashes for every dependency including transitive dependencies. ensures reproducible builds. never hand-edited.

### local cache

```
~/.v2/cache/
  github.com/
    user/
      router/
        v0.3.1/
          v2.pkg
          src/
```

packages are git-cloned at the specified version. the cache mirrors the git path.

### CLI

- `v2 init` - create v2.pkg in the current directory
- `v2 add <url> [version]` - add a dependency
- `v2 install` - fetch all dependencies
- `v2 update [pkg]` - update to latest compatible version

### import resolution for packages

packages are imported by the `name` field from their v2.pkg:

```
imp router { serve, get, post }
```

if two packages export the same name, alias one:

```
imp router as r
imp other_router as r2
```

the compiler searches: stdlib first, then local files, then packages.

## FFI

calling C functions from v2:

```
extern "c" {
  fn getpid() -> i32
  fn strlen(s: cstr) -> i32
}
```

`extern "c"` declares functions from libc. other library names resolve via the platform's dynamic linker:

```
extern "sqlite3" {
  fn sqlite3_open(path: cstr, db: &mut ptr) -> i32
  fn sqlite3_close(db: ptr) -> i32
}
```

### FFI types

| v2 type | C type | notes |
|---------|--------|-------|
| `cint` | `int` | 32-bit signed |
| `cstr` | `const char*` | null-terminated |
| `ptr` | `void*` | raw pointer |
| `&mut ptr` | `void**` | pointer to pointer |
| `f64` | `double` | |
| `f32` | `float` | |

v2 strings are automatically null-terminated when passed as `cstr` (a copy is made with a null byte appended). C strings returned as `cstr` are copied into GC-managed memory. null pointers returned from C become `nil`.

**GC safety with FFI:** C code that holds pointers to v2 heap objects must pin them to prevent the GC from moving or collecting them. `pin(value)` prevents collection until `unpin(value)` is called. pinned objects are added to a root set that the GC always considers live. forgetting to unpin is a memory leak, not a crash.

```
data = [1, 2, 3, 4, 5]
pin(data)
c_process(data.ptr, data.len)
unpin(data)
```

## unsafe

most code never needs `unsafe`. it exists for FFI interop and low-level operations that the type system can't verify.

an `unsafe` block allows:
- raw pointer arithmetic (`ptr.offset(n)`, `ptr.read()`, `ptr.write(val)`)
- casting between unrelated types (`cast(val, TargetType)`)
- calling C functions declared in `extern` blocks
- accessing `pin`/`unpin` for GC pinning

```
unsafe {
  raw = cast(data.ptr, ptr)
  value = raw.offset(4).read(i32)
}
```

`extern` function calls are implicitly unsafe - they don't need an `unsafe` block at the call site. the `extern` declaration itself is the opt-in. this keeps FFI ergonomic. wrapping every C call in `unsafe { }` would be tedious without adding safety.

`pin` and `unpin` are only available inside `unsafe` blocks or at module scope in FFI-heavy code. forgetting to `unpin` is a memory leak.

code inside `unsafe` can still use all normal language features. `unsafe` only unlocks additional operations - it doesn't disable safety checks on normal code.

a function can be marked `unsafe` to signal that calling it requires care:

```
unsafe fn raw_write(addr: ptr, val: i32) {
  addr.write(val)
}

// caller must use unsafe block
unsafe {
  raw_write(some_ptr, 42)
}
```

## testing

test blocks can appear in any file:

```
fn add(a: int, b: int) -> int = a + b

test "addition" {
  assert_eq(add(2, 3), 5)
  assert_eq(add(-1, 1), 0)
}

test "parse error" {
  result = parse("")
  assert(result.is_err())
  assert(result.err_msg().contains("empty"))
}
```

`v2 test` discovers and runs all test blocks across all files. tests run in parallel by default (each test in its own task). test failures report the file, line, assertion, and values.

`v2 test file.v2` runs tests in a specific file. `v2 test -f "parse"` filters by test name.

test blocks are stripped from production builds (`v2 build`). they only exist in test builds.

## stdlib

### std/io
`print(val)`, `println(val)`, `eprint(val)`, `eprintln(val)`, `readln() -> str?`. buffered readers and writers for streaming I/O: `reader(file) -> Reader`, `writer(file) -> Writer`. readers yield lines or chunks.

### std/fs
`read(path) -> str!`, `write(path, content) -> !`, `append(path, content) -> !`, `exists(path) -> bool`, `remove(path) -> !`, `mkdir(path) -> !`, `readdir(path) -> [str]!`, `walk(path) -> iter(str)`. all operations return results - no silent failures.

### std/os
`env(key) -> str?`, `args() -> [str]`, `exit(code)`, `exec(cmd, args) -> ExecResult!`. `ExecResult` has `stdout: str`, `stderr: str`, `status: int`.

### std/json
`encode(val) -> str` serializes any value. `decode(s) -> T!` deserializes into a typed value (the target type is inferred or specified). structs map to JSON objects by field name. enums map to `{"type": "VariantName", "value": payload}`.

### std/net
`listen(host, port) -> Listener!`, `accept(l) -> Conn!`, `connect(host, port) -> Conn!`, `read(conn) -> str!`, `write(conn, data) -> !`, `close(conn)`, `timeout(conn, ms)`. UDP: `udp_bind(host, port) -> Socket!`, `sendto(sock, data, host, port) -> !`, `recvfrom(sock) -> Packet!`.

### std/http
**client:** `get(url) -> Response!`, `post(url, opts) -> Response!`, `fetch(opts) -> Response!`. `Response` has `status: int`, `headers: str`, `body: str`. streaming: `stream_open(opts) -> Reader!`, `stream_read(reader) -> str?`, `stream_close(reader)`.

**server:** `serve(addr, config)` starts an HTTP server. route constructors: `get(path, handler)`, `post(path, handler)`, `put(path, handler)`, `patch(path, handler)`, `delete(path, handler)`, `ws(path, handler)`. handlers receive a `Request` and return a `Response`. each handler runs in an implicit arena.

```
serve(":8080", [
  get("/users/:id", fn(req) -> Response {
    id = req.params["id"]
    user = db.find(id) or return not_found()
    return json(user)
  }),
  post("/users", fn(req) -> Response {
    user = json.decode(req.body, User) or return status(400, "invalid body")
    db.insert(user) or return status(500, "db error")
    return created(user)
  }),
])
```

`serve` accepts either an array of routes or a config map with `middleware` and `routes` keys (see middleware section below).

if a handler panics, the server catches the panic, logs it, and returns a 500 response. handlers should use `or` to handle errors explicitly rather than relying on this safety net.

`Request` fields: `method: str`, `path: str`, `headers: {str: str}`, `body: str`, `params: {str: str}` (route params from `:name` segments), `query: {str: str}` (query string parameters).

`Response` constructors: `ok(body)`, `json(val)`, `created(val)`, `not_found()`, `redirect(url)`, `status(code, body)`, `response(code, headers, body)` for full control.

**middleware:** a middleware is a function that takes a handler and returns a handler. handlers have type `fn(Request) -> Response`. middleware wraps them:

```
fn logging(handler: fn(Request) -> Response) -> fn(Request) -> Response {
  return fn(req) -> Response {
    start = time.now()
    res = handler(req)
    elapsed = time.since(start)
    println("{req.method} {req.path} {res.status} {elapsed}ms")
    return res
  }
}

fn cors(origins: str, handler: fn(Request) -> Response) -> fn(Request) -> Response {
  return fn(req) -> Response {
    res = handler(req)
    return response(res.status, {
      ...res.headers,
      "Access-Control-Allow-Origin": origins,
    }, res.body)
  }
}
```

middleware composes by wrapping:

```
handler = cors("*", logging(fn(req) -> Response {
  return ok("hello")
}))
```

or apply middleware to an entire server with `use`:

```
serve(":8080", {
  middleware: [logging, cors("*"), auth(secret)],
  routes: [
    get("/users", list_users),
    post("/users", create_user),
  ],
})
```

when `middleware` is provided, each middleware wraps every route handler. they execute in order: the first middleware in the list is the outermost wrapper. in the example above, a request flows through `logging -> cors -> auth -> handler`.

**websockets:** `ws(path, handler)` creates a WebSocket route. the handler receives a `WsConn` for bidirectional communication:

```
serve(":8080", {
  routes: [
    get("/api/status", fn(req) -> Response { return ok("up") }),
    ws("/feed", fn(conn: WsConn) {
      for msg in conn {
        // msg is a string received from the client
        conn.send("echo: {msg}")
      }
      // loop exits when the client disconnects
    }),
  ],
})
```

`WsConn` methods:
- `conn.send(msg: str)` - send a text message to the client
- `conn.close()` - close the connection
- `for msg in conn` - iterate over incoming messages. the loop exits when the client disconnects or the connection is closed

WebSocket handlers run in their own task. each connection is independent.

### std/tls
`upgrade(conn, hostname) -> TlsConn!` for client TLS. `context(cert, key) -> TlsCtx!` for server TLS. TLS connections implement the same `read`/`write` interface as plain connections.

### std/term
`cols() -> int`, `rows() -> int`, `size() -> Size`, `is_tty() -> bool`. cursor: `move(row, col)`, `up(n)`, `down(n)`, `save()`, `restore()`, `hide_cursor()`, `show_cursor()`. screen: `clear_line()`, `clear_screen()`. input: `raw()`, `cooked()`, `read_key() -> str?`. style: `style(text, opts) -> str` applies ANSI styling. returns plain text when not a TTY.

### std/time
`now() -> Time`, `sleep(ms)`, `since(t) -> Duration`, `format(t, fmt) -> str`, `parse(s, fmt) -> Time!`. `Duration` supports arithmetic. `Time` is nanosecond-precision.

### std/crypto
`sha256(data) -> [byte]`, `blake3(data) -> [byte]`, `hmac(key, data, hash_fn) -> [byte]`, `random_bytes(n) -> [byte]`. no encryption primitives in stdlib - use FFI to libsodium or openssl for that. hashing and authentication only.

### std/log
`info(msg)`, `warn(msg)`, `error(msg)`, `debug(msg)`. structured fields: `info("request handled", { method: "GET", path: "/users", ms: 12 })`. output format is JSON by default. configurable via `log.config({ level: "info", format: "text" })`.

### std/regex
`match(pattern, text) -> Match?`, `find_all(pattern, text) -> [Match]`, `replace(pattern, text, replacement) -> str`. `Match` has `text: str`, `start: int`, `end: int`, `groups: [str?]`. patterns are compiled on first use and cached.

### std/sql
`connect(driver, dsn) -> Conn!`, `query(conn, sql, params) -> Rows!`, `exec(conn, sql, params) -> ExecResult!`. `Rows` is an iterator of row objects. rows are accessed by column name: `row["name"]` returns `Value` (a tagged union of int/float/str/bool/nil). `decode(row, T) -> T!` maps a row to a struct using `@sql` tags (falls back to field names for untagged fields). prepared statements: `prepare(conn, sql) -> Stmt!`, `stmt.query(params)`, `stmt.exec(params)`. drivers for postgres and sqlite are included.

## tooling

### v2 run
compile and execute. uses tcc for fast compilation by default. `v2 run --release file.v2` uses cc -O2.

### v2 build
compile to native binary. uses cc -O2 by default. `v2 build file.v2 -o myapp`. `v2 build --emit-c file.v2` outputs the generated C file. `v2 build --cc=zig-cc file.v2` uses an alternate C compiler.

### v2 test
discover and run all test blocks. `v2 test` runs everything. `v2 test file.v2` runs one file. `v2 test -f "pattern"` filters by name. output shows pass/fail with file:line for failures and the actual vs expected values.

### v2 fmt
canonical formatting. tabs for indentation. one true style - no configuration. `v2 fmt .` formats all .v2 files in the current directory recursively. `v2 fmt --check .` exits nonzero if any file would change (for CI).

### v2 lsp
language server protocol over stdio. capabilities: hover (type info + doc comments), completions (builtins, stdlib, user definitions, imports), go-to-definition (including cross-module), find references, rename, diagnostics (parse errors + type errors), signature help, code actions (import suggestions).

### v2 doc
generate HTML documentation from doc comments (lines starting with `//` directly above a pub declaration). `v2 doc .` generates docs for the current package. output includes function signatures, type definitions, and cross-links.

## what this is

a language for building applications. it compiles to native code. the type system catches bugs. the GC handles memory. arenas handle the hot paths. the syntax is small enough to learn in a day.

the competition is Go. same niche, but with a real type system (generics, algebraic types, exhaustive matching, option/result instead of `if err != nil`), better ergonomics (UFCS, inference, immutable by default, closures), and the same simplicity.

## what this is not

not a systems language. not for kernels, drivers, or embedded. the GC and runtime are non-negotiable. use Zig or Rust.

not a scripting language. no REPL, no eval, no dynamic types. use Python or Lua.

not an experiment. every feature earns its complexity by making real programs better. features that don't are not included.
